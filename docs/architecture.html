System Architecture

A modular monolith. One backend process serves the API and both frontends. No microservices, no build step, no framework on the client.

Tech stack

APIFastAPI (Python), sync route handlers (not async def) — matches the SQLAlchemy-sync-session convention used throughout
ORM / DBSQLAlchemy 2.0 + PostgreSQL 16, Alembic for migrations
AuthJWT (python-jose), two independent token types (staff vs. customer) sharing one secret but disambiguated by a type claim
FrontendVanilla HTML/CSS/JS — no React/Vue, no bundler, no npm build. Pages are static files served directly by FastAPI's StaticFiles/FileResponse
PaymentsStripe (Checkout Sessions, Connect Standard accounts, Subscriptions, webhooks)
EmailResend (transactional email for notifications/welcome messages)
Rate limitingslowapi, in-memory backend (correct for this single-process deployment)
ContainerDocker Compose — two services, backend and db

Why a modular monolith

Everything runs as one Python process. This was a deliberate choice, not a limitation: the app is a set of related admin/ordering workflows for a single restaurant business at a time, not a system with independently-scaling components. A monolith means one deployment, one database connection pool, one thing to monitor — appropriate for the actual scale (a handful of restaurants, not thousands of concurrent tenants) and dramatically simpler to build, debug, and host without a credit card.

Two frontends, one backend

The single FastAPI process serves three distinct surfaces:

Staff app

frontend/*.html + frontend/js/*.js. POS checkout, inventory, orders, reports, admin. JWT auth, permission-gated.

Customer site

frontend/site/*.html + frontend/site/js/*.js. Menu browsing, cart, checkout, reservations, account. Separate JWT auth (or fully anonymous/guest).

REST API

/api/* for staff, /api/public/* for customers. Documented in API Reference.

Both frontends are plain static files with no build step — a page links to the next page with a normal <a href>, and JS talks to the API with plain fetch(). This keeps local development trivial: edit a file, refresh the browser.

Request flow — a checkout, end to end

  1. Customer browses /t/{slug}/site/menu.html, adds items to a cart (stored in localStorage).
  2. POST /api/public/checkout — validates stock, prices every line server-side (never trusts a client-sent price), reserves inventory immediately (before payment, to prevent overselling), creates an Order in fulfillment_status=pending.
  3. Creates a Stripe Checkout Session on the restaurant's own connected Stripe account (stripe_account=...) — the charge goes straight to them, not the platform. See Payments.
  4. Customer is redirected to Stripe's hosted checkout page, pays.
  5. Stripe fires a webhook to /api/public/webhooks/stripe-connect — signature verified, order looked up by metadata.order_id, flipped to confirmed, a confirmation email queued, and a WebSocket broadcast pushed to any open Kitchen Display / Online Orders screens for that business.
  6. Staff sees the order appear within ~1 second via the WebSocket push (polling every 15s remains as a fallback if the socket drops).

Real-time updates

An in-process ws_manager.py tracks connected WebSocket clients (each staff connection is authenticated by JWT at connect time and tagged with its business_id) and broadcasts order-changed events. Since routes are synchronous, a broadcast from a sync handler schedules itself onto the async event loop via asyncio.run_coroutine_threadsafe() — the event loop reference is captured once at app startup.

Broadcasts are filtered by business_id so one tenant's Kitchen Display never sees another tenant's orders — verified directly by intercepting the actual WebSocket messages in two simultaneous browser sessions.

Project structure

├── backend/

│   │   ├── api/            # one file per route group (~32 files)

│   │   ├── models/          # SQLAlchemy models (~20 files)
│   │   ├── schemas/         # Pydantic request/response models
│   │   ├── services/        # business logic shared across routes
│   │   ├── main.py          # app assembly, routing, static file serving
│   │   ├── seed.py          # idempotent demo data
│   │   └── create_tenant.py # CLI tenant creation
│   ├── alembic/versions/    # migration history
│   └── scripts/             # backup_db.sh / restore_db.sh
├── frontend/
│   │   ├── *.html, js/      # staff app (~25 pages)
│   │   └── site/            # customer site (~12 pages)
