Multi-Tenancy

One deployment, many restaurants, each provably unable to see another's data. Shared database, row-level isolation.

The core mechanism

Every tenant-owned table has a business_id column. A global SQLAlchemy query filter — installed per-request, not opted into per-query — automatically scopes every ORM SELECT to the current tenant. No individual route's read logic had to be rewritten.

The Business model

The tenant root. Every other table's business_id points here. Also holds what used to be a separate singleton settings table — currency symbol, VAT rate, receipt footer, address — since a business's own settings are naturally per-tenant, not global.

How a request gets scoped

TenantMiddleware (Starlette middleware, runs before any FastAPI dependency) resolves business_id for every request, in priority order:

  1. JWT claim — if the request carries a valid staff or customer token, business_id is read directly from it (added to the token at login/signup). Cryptographically tied to the account, can't be spoofed by a client-supplied header.
  2. /t/{slug}/ path prefix — for anonymous requests to a tenant-prefixed page.
  3. X-Business-Slug header — for anonymous API calls made from a /t/{slug}/ page (the API itself lives at /api/..., not under /t/{slug}/, so the frontend's shared fetch helper reads the slug out of its own page URL and attaches it as a header).

The resolved business_id lands on request.state.business_id, which get_db() reads to install the filter on that request's database session:

def get_db(request: Request):
    db = get_scoped_session(request.state.business_id)
    try:
        yield db
    finally:
        db.close()

get_scoped_session() attaches a with_loader_criteria event listener scoped to that one session instance — every SELECT for any model in the TENANT_SCOPED_MODELS registry gets WHERE business_id = :tenant_id appended automatically.

A real bug this caught

The filter's lambda originally captured tenant_id via a tid=tenant_id default-argument trick (to dodge Python's classic closure late-binding bug). That accidentally broke SQLAlchemy's statement-cache key tracking, which inspects genuine lexical closures, not default arguments — the first tenant to log in got its filter compiled and cached, and every other tenant's session silently reused that cached plan. Caught by testing alternating logins between two tenants, not just one in isolation. Fixed by using a real closure instead of the defensive default-arg pattern.

Writes still need explicit stamping

The filter only protects reads. Every Model(...) construction for a tenant-owned row needs business_id=... set explicitly. Most creation endpoints get this for free — they already take current_user/current_customer as a dependency, and business_id is a real column on those objects now. Only genuinely anonymous writes (guest checkout, guest reservation, newsletter signup) read it from request.state.business_id instead.

Anonymous public endpoints need an explicit guard

A real gap this caught

Without a resolved business_id, get_db() installs no filter at all — an unscoped query returns every tenant's rows mixed together. Discovered live: hitting /api/public/menu with no X-Business-Slug header returned Bavaria Genuss's full menu to anyone. Fixed with a shared require_tenant dependency applied to every anonymous public read endpoint (menu, discounts, tables, recommendations, reviews) — rejects with 400 instead of silently running unscoped. The Stripe webhook endpoint is a deliberate, reviewed exception: it must look up an order by ID with no tenant context, since Stripe itself doesn't know or send tenant info.

WebSockets

No Request object exists in a WebSocket handler, so it can't use get_db() as a dependency. It decodes the JWT itself and calls get_scoped_session(business_id) directly. Each tracked connection is tagged with its business_id, and broadcasts filter recipients to matching connections only.

URL structure

/t/{slug}/Staff app entry point (login, then all staff pages)
/t/{slug}/site/Customer ordering site for that tenant
/signup.htmlSelf-serve tenant creation (no slug yet — this is what assigns one)
/, /site/Unprefixed fallback — renders but can't authenticate (no tenant to resolve)

Static assets (CSS/JS/icons) stay unprefixed and shared — identical code across every tenant, only data differs. Page navigation uses relative hrefs (menu.html, not /site/menu.html) so the browser naturally preserves whichever prefix the current page is under, with zero JS required.

Reserved slugs

A small blocklist (api, t, css, js, uploads, site, admin, www, static) is rejected at signup — these don't actually collide with any route (tenant pages live under a distinct /t/ namespace) but would be confusing or spoofable if allowed.

Creating a tenant

Both the self-serve /signup.html flow and the create_tenant.py CLI script call the same shared tenant_service.create_business() — one implementation of "what a brand-new business looks like": a Business row, a default Store, and a first admin User.

Verifying isolation

The test that actually proves isolation (not just that the UI hides things): take a valid JWT from Tenant B, request Tenant A's order by ID. The response is 404, not 403 — the row is invisible to the query, not merely permission-blocked. That distinction matters: a 403 means the app checked and denied; a 404 from an unscoped-but-permission-checked query would mean the isolation depends entirely on that one check never being missed anywhere. A 404 from the global filter means the row doesn't exist as far as that session can see, structurally, regardless of which endpoint asks.
