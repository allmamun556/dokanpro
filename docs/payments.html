Payments

Two completely separate money flows, on two separate Stripe accounts. Don't confuse them.

Diner → Restaurant

Stripe Connect (Standard accounts). A diner's payment goes straight to that restaurant's Stripe balance. The platform never touches this money.

Restaurant → Platform

Stripe Subscriptions, on the platform's own Stripe account. Flat monthly fee, unrelated to Connect. This is your revenue.

Stripe Connect — diner payments

Why Standard accounts specifically: least platform liability. The connected account is genuinely the restaurant's own Stripe account — the platform can create it and generate onboarding links, but cannot fill in the restaurant's business details, bank account, or accept their Terms of Service on their behalf. That's a deliberate Stripe security boundary (confirmed directly: the platform's API key gets a PermissionError if it tries), and it's exactly why Standard has the lowest support/compliance burden of Stripe's Connect account types.

Onboarding flow

  1. Staff clicks "Connect Stripe" in Settings → POST /api/settings/stripe/connect.
  2. Backend creates a Standard connected account (stripe.Account.create(type="standard", ...)) if one doesn't exist yet, saves stripe_account_id on the Business row.
  3. Creates a single-use Account Link and returns its URL — Stripe's current recommended flow for Standard accounts.
  4. Restaurant owner completes real KYC on Stripe's hosted page (business details, bank account, ToS).
  5. Redirected back to /t/{slug}/settings.html?stripe_return=1, which re-fetches status — GET /api/settings/stripe/connect/status calls stripe.Account.retrieve() and updates stripe_charges_enabled.

Checkout is gated on stripe_charges_enabled

If a business hasn't finished onboarding, checkout returns a clean 400 ("This restaurant hasn't finished setting up online payments yet") instead of silently accepting payment into the platform's own account. This is the single most important safety property of the whole integration — verified directly, before and after connecting.

How the charge actually routes

The Checkout Session is created with stripe_account=business.stripe_account_id — this single parameter is the entire mechanism. Making the API call "as" the connected account means Stripe creates the session (and the resulting charge) directly on their books, not the platform's. No application fee, no fund transfer step — confirmed by retrieving the created session and finding it's only visible with that stripe_account header, i.e. it genuinely lives on their account.

Webhooks — two separate endpoints

This is not optional plumbing

Stripe does not deliver connected-account events to a platform's normal webhook endpoint. A separate endpoint must be registered specifically as a "Connect" webhook (connect: true in the Dashboard, or stripe listen --forward-connect-to locally), with its own signing secret. Confirmed against current Stripe docs before building this, not assumed.

EndpointSecretHandles
/api/public/webhooks/stripe-connectSTRIPE_CONNECT_WEBHOOK_SECRETDiner order payment events — checkout.session.completed / .expired, from any connected account
/api/public/webhooks/stripeSTRIPE_WEBHOOK_SECRETPlatform-side subscription events

Order lookup on the connect webhook works identically regardless of which connected account the event came from — by metadata.order_id, set at session creation.

Stripe Subscriptions — platform billing

A business subscribes from Settings → POST /api/billing/subscribe creates/reuses a platform-side stripe.Customer for that business and a Checkout Session in mode="subscription" — no stripe_account parameter, this runs entirely on the platform's own account.

The webhook (/api/public/webhooks/stripe) handles:

  • checkout.session.completed (subscription mode) → saves stripe_customer_id / stripe_subscription_id, sets subscription_status = "active"
  • customer.subscription.updated / .deleted → updates subscription_status from the event's own status string (stored verbatim — active, past_due, canceled, etc. — rather than a parallel local enum that could drift out of sync with Stripe's own model)

Deliberately not enforced yet

Subscription status is tracked and visible, but nothing currently blocks access for a lapsed or missing subscription — a product decision, not an oversight. See Roadmap.

Local testing

Two things Stripe's hosted UI actively resists in headless browser automation, as a legitimate anti-fraud measure — both worked around the same way, by verifying the underlying mechanism via the Stripe API/CLI directly instead of fighting the UI:

  • Checkout page payment completion — verified via stripe trigger checkout.session.completed --override checkout_session:metadata.order_id=N (with --stripe-account for the connect webhook), which fires a real signed event without needing a completed card form.
  • Connect onboarding KYC — verified at the API level (account creation, account link generation, the charges-enabled gate, the actual charge routing) rather than pushing a test account through the full hosted onboarding form.

stripe listen \
  --forward-to localhost:8000/api/public/webhooks/stripe \
  --forward-connect-to localhost:8000/api/public/webhooks/stripe-connect
