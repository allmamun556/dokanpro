Roadmap & Status

An honest accounting of what's built and verified, what's deliberately deferred, and what would actually block selling this to strangers.

Built and verified

DoneCore POS — checkout, inventory, purchasing, suppliers, transfers, expenses, reporting
DoneRestaurant platform — online ordering, reservations, kitchen display, table QR ordering, loyalty points, reviews
DoneMulti-tenancy — real row-level isolation, verified with a negative test (cross-tenant request returns 404, not 403)
DoneSelf-serve signup — a restaurant owner can create their own tenant without anyone running a script for them
DoneStripe Connect — diner payments route to each restaurant's own account, not the platform's
DoneStripe Subscriptions — platform billing wired up and tracked
DoneRate limiting, input validation, backup/restore scripts
DonePWA correctness — per-tenant install manifest, offline menu caching
DoneVisual design — "Warm & Craft" system applied consistently across staff app + customer site

Deliberately deferred (not oversights)

Tracked, not enforced Subscription paywall

A lapsed or missing subscription is recorded but doesn't block access yet. Chosen explicitly — enforcement means deciding grace periods and which features (if any) stay accessible, real scope not needed until you're ready to actually rely on payment mattering.

Standard accounts only No per-transaction platform fee

Revenue is subscription-only. A transaction-based cut would need Express/Custom Connect accounts instead of Standard — more platform liability and support burden, a genuinely separate piece of work if wanted later.

No verification gate Email verification

Neither customer registration nor business signup blocks on verifying the email address — matches the existing "MVP-first" precedent throughout this build.

What would actually block selling this publicly

Blocker No legal documents

No Terms of Service, Privacy Policy, or Data Processing Agreement. Not a formality — the moment a second real business signs up, this is a genuine compliance requirement (GDPR applies). Needs a lawyer or a template service (Termly, iubenda) filled in with real business details — this is not something that can be drafted as generic boilerplate.

Blocker Real Stripe Connect onboarding never completed by a human

Verified thoroughly at the API level (account creation, charge routing, webhooks), but nobody has walked through Stripe's actual hosted KYC flow end to end — it resists headless browser automation as an anti-fraud measure. A real business's onboarding could surface friction not yet seen.

Not yet exercised Real deployment

Everything has run in local Docker Compose. Deploying to a real host (see Deployment) always surfaces something — env vars, cold starts, migration against a real remote database.

Missing Error monitoring

No Sentry or equivalent. If something breaks for a real customer, the first sign of it today would be them telling you, not an alert.

Recommendation

Not "flip a switch and sell publicly." A small, trusted beta — one or two real restaurants, told explicitly it's early, possibly free for the first few months in exchange for feedback. That exercises the real Connect onboarding, a real subscription payment, and real usage patterns with people who'll forgive rough edges, before taking money from strangers who won't.
