Roles & Permissions

Five roles, seventeen fine-grained permission keys, per-user overrides. Enforced server-side on every mutating endpoint — the frontend hiding a nav link is a courtesy, not the security boundary.

How it's enforced

def has_permission(user: User, key: str) -> bool:
    overrides = user.permission_overrides or {}
    if key in overrides:
        return bool(overrides[key])
    return key in ROLE_DEFAULTS.get(user.role, set())

Per-user permission_overrides (a JSON column) take priority over the role default — an admin can grant or revoke any individual key for any individual user without changing their role. Routes declare a requirement via a dependency:

@router.post("/refund", dependencies=[Depends(require_permission("orders.refund"))])

Frontend nav mirrors this, doesn't replace it

The staff app's grouped dropdown navigation (Sales / Inventory / Customers / Admin) filters every item by the same permission/role check before rendering — a cashier never even sees a "Users" link. But that's UX, not security: the actual API endpoint checks the permission independently on every request, regardless of what the frontend chose to show.

Two entirely separate auth systems

Staff permissions have no bearing on the customer-facing site — a logged-in customer's JWT carries type: "customer", not a role, and customer-facing endpoints just check "is this a valid customer" or "does this customer own this order/reservation," never a permission key. See API Reference.
