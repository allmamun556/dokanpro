Security & Hardening

Rate limiting, input validation, and backups — the difference between "works when it's just us testing" and "safe with strangers' businesses depending on it."

Rate limiting

slowapi, in-memory backend — correct for this single-process deployment, no Redis needed. A shared Limiter keyed by client IP, registered once in main.py, with a custom 429 handler matching the app's standard {"detail": "..."} error shape.

Why checkout's limit actually matters

Stock is reserved at order creation, before payment — necessary so the Stripe redirect can never oversell the last portion of a dish. Without a rate limit, that's an abuse path: spam fake checkout requests to artificially exhaust a restaurant's displayed stock without ever paying. Verified directly by hammering the endpoint and confirming the 11th request in a minute gets a 429.

Input validation

Unbounded query parameters

Six list endpoints (orders, inventory ×2, purchases, notifications, transfers, reports/top-products) accepted an unbounded limit query param — a client could request limit=999999999 and force an unbounded query. Capped with Query(default, le=500) (or le=100/le=1000 where the existing default implied a different sane ceiling).

Unbounded quantities

Order/refund line-item quantities had no upper bound (only qty > 0). Capped at le=100 — a sane ceiling for a diner order, with inventory checks still catching the realistic worst case underneath. Purchase-order quantities (wholesale restocking, staff-only) get a much higher ceiling, le=100000, since that's a genuinely different context.

Caught during verification, fixed before it shipped

A mechanical edit added Query(...) to six files but missed importing Query in one of them — crashed the whole container on startup with a NameError. Caught by rebuilding and checking docker compose ps immediately after, not assumed to have worked.

Backups

backend/scripts/backup_db.sh / restore_db.sh — a manual (or cron-triggered) pg_dump/restore pair, not scheduled or shipped off-site automatically. Verified for real: a backup was taken, restored into a scratch database (not the live one), confirmed the data came back correctly, then torn down.

./backend/scripts/backup_db.sh
./backend/scripts/restore_db.sh backups/pos_db_20260730_170928.sql

restore_db.sh is destructive (drops and recreates the schema) and requires typing yes to confirm.

Why this stays manual for now

True automated/scheduled/off-site backups depend on a hosting decision that hasn't been made yet — most managed Postgres providers (Neon included) include this for free once you're on one. Building custom scheduling infrastructure now would likely be thrown away. See Deployment.

What's explicitly out of scope

  • Distributed rate-limit storage (Redis) — would only matter if this ever ran multiple backend replicas; it doesn't.
  • Exhaustive max-length validation on every public string field — most rely on the database column length today, which surfaces as a 500 instead of a clean 422. Flagged, not silently ignored.
  • CAPTCHA / bot-detection beyond rate limiting.
  • IP allowlisting or WAF-type protections.
